# 性能测试面试要点

> 配合本仓库的实际做法来背：每个问题先给结论，再给"我们项目里怎么做"的例子。
> 标注【待填】的地方，等真实压测数据出来后替换成自己的数字。

## 1. TPS 和 QPS 有什么区别？

- **QPS**（Queries Per Second）：每秒查询数，通常指每秒的 HTTP 请求量。
- **TPS**（Transactions Per Second）：每秒事务数，一个"事务"可以是业务意义上的完整操作，可能包含多个请求。
- 在接口压测里两者经常被混用。本项目里每个 Locust task 就是一个事务（如一次列表查询），所以 TPS ≈ QPS；区别在于：如果一个事务 = 登录 + 查列表两步，那 TPS 就是 QPS 的一半左右。面试时先给定义，再说"我的场景里二者数值一致，因为一个事务就一个请求"。

## 2. P90 / P95 / P99 是什么？为什么不用平均值？

- P99：99% 的请求响应时间都低于这个值，即**长尾**里最慢的那 1%。
- 平均值会被大量快请求稀释：1000 个请求里 990 个 50ms、10 个 5s，平均才 99ms，看起来还行，但那 10 个用户已经卡了 5 秒。P95/P99 直接暴露这部分糟糕体验。
- Locust 的 CSV 里每一行是当前统计窗口的瞬时分布，`*_stats.csv` 里是整个 run 的累计分布；报告里两个都看：拐点分析用窗口值（趋势），结论用累计值（总体）。

## 3. 怎么判断瓶颈在 CPU、内存、还是数据库？

核心方法：**压测指标 + 资源监控交叉验证**，单看一边都是猜。

| 现象组合 | 结论 |
|---------|------|
| CPU 打满 + RT 升高 + TPS 不再涨 | 计算瓶颈（如本项目 bcrypt 登录就是故意耗 CPU 的哈希） |
| CPU 不满 + RT 高 + 出现 `database is locked` | 锁/IO 等待（SQLite 单写者瓶颈） |
| CPU 不满 + RT 高 + 内存 swap / GC 频繁 | 内存瓶颈 |
| 多核机器只有单核忙 | 进程/线程模型上限（如 uvicorn 单 worker + 同步框架） |

本项目用 `scripts/monitor.py`（psutil）按秒采集被测进程的 CPU/内存，与 Locust 的时间序列对齐分析。
实测案例：混压场景 100 并发起吞吐崩到 ≈0，但进程 CPU 仅 0~2% → 排除算力瓶颈；结合服务端日志
`QueuePool limit of size 5 overflow 10 reached, connection timed out, timeout 30.00` → 锁/池化等待实锤；
登录专项 10 并发即单核 88% → 认证是独立的计算瓶颈。三个瓶颈用同一组交叉验证数据区分开。

## 4. 为什么选 Locust 而不是 JMeter？

1. **脚本即代码**：locustfile 是 Python，能进 Git、能 code review、能复用项目里的登录/造数逻辑；JMeter 的 .jmx 是 XML，diff 出来没法看。
2. **技术栈统一**：整个体系（被测系统、API 自动化、UI 自动化）都是 Python，压测也用 Python，维护成本低。
3. **自定义负载曲线直观**：`LoadTestShape` 十几行代码实现阶梯加压；JMeter 要配多个线程组 + 定时器拼接。
4. JMeter 的优势是 GUI 录制、协议广、不写代码；对本项目这种"少接口、深分析"的场景，Locust 更合适。

## 5. 为什么单 worker 压测？

`uvicorn --workers 1` 是刻意保留的：先测出**裸服务的真实上限**。FastAPI 的同步接口跑在单 worker 的线程池里，并发能力天然有限；如果一上来就 4 个 worker，瓶颈会被掩盖。多 worker 对比实验反而是报告的优化素材——但要注意 SQLite 是文件锁，多进程写会互相踩，这正好引出"生产环境应换 PostgreSQL"的结论。

## 6. 为什么登录接口单独建模（单独一个 locustfile）？

1. **开销性质不同**：bcrypt 校验是 CPU 密集型（故意设计得慢，~100ms 量级），读写接口是 IO 密集型。混在一个场景里，登录的 CPU 瓶颈会污染读写接口的数据，列表/详情的"真实"上限测不出来。
2. **可独立定位**：分开压，登录 TPS 到某个数就封顶而 CPU 单核满 → 认证是独立瓶颈，结论是"认证服务应独立扩容"；混压则只能得到一团浆糊。
3. 真实系统里认证也确实是独立服务，建模更接近生产。

## 7. 为什么造数和压测分离（seed_data.py 独立于 locustfile）？

1. **注册极贵**：注册要走 bcrypt 哈希，几百毫秒一次。放进压测任务等于自己制造 CPU 瓶颈，测出来的是"注册接口压测"而不是业务场景。
2. **数据可控可重复**：账号池、文章 ID 落到 seed_ids.json，每轮压测的数据规模一致，优化前后对比才有意义。
3. Locust 的 `on_start` 只做轻量的登录拿 Token（登录开销本身就压得起，登录专项另测）。

## 8. 压测机和被测机同机，有什么影响？

Locust 200 并发（gevent 协程）自己也吃 CPU，和被测服务抢核会把**拐点提前**（测出来的上限偏低）。解决：另一台机器/Docker 分开跑；条件不允许时必须在报告"测试环境"里如实声明，并尽量降低干扰（压测端 wait_time 拉开、关掉无关程序）。如实声明同机是加分项，隐瞒是扣分项。

## 9. SQLite 的 `database is locked` 是怎么回事？

SQLite 整库一把写锁，同一时刻只允许一个连接写。并发写请求排队超时（默认 busy timeout 5s）就报这个错。**压测里出现它不是 bug，是结论**：记录出现的并发数、错误率，作为"SQLite 不适合高并发写"的证据。对应优化见第 10 条。

## 10. WAL 模式是什么？为什么能提升读写混合性能？

- 默认 journal 模式（rollback journal）：写事务会阻塞读，读也会阻塞写，读写互斥。
- WAL（Write-Ahead Logging）：写追加到 -wal 文件，读继续走主库，**读写不再互斥**，只有写-写仍然串行。
- 一行 PRAGMA 开启（本项目在 `app/database.py` 的 engine connect 事件里执行 `PRAGMA journal_mode=WAL`），对"读多写少"的博客场景收益明显。
- **本项目实测**：WAL 与连接池扩容、login 改同步一起部署在 perf-opt 分支；读多写零的压测场景里 WAL 没有直接 TPS 收益（读本来就不互斥），它的价值在写并发——busy_timeout=30s 让写锁等待而不是立刻 `database is locked`。归因时要诚实：读场景的提升来自另外两项优化（CPU 多核占用是直接证据）。
- 边界：WAL 解决读写互斥，不解决写-写冲突；并发写更高时还是要换客户端/服务端数据库（PostgreSQL + 连接池）。

## 13. FastAPI 的 async 接口里能不能跑 CPU 密集操作？（本项目最重要的教训）

**不能。** `async def` 端点直接跑在事件循环上，循环是单线程的：bcrypt 校验一次 ~250ms，期间**整个服务**（所有接口、所有连接）都停摆。本项目实测证据链：

1. 登录专项：`async def login` 时 10 并发就把单核打到 88%，TPS 封顶 ~4/s；
2. 混压场景：每级爬坡的登录风暴阻塞循环 → 线程池占满 → 连接池 checkout 排队 30s 超时 → 246 次 HTTP 500，拐点出现在 50→100 并发；
3. 高压退场后服务"假死"（进程活着但不 accept，CPU≈0），重启才恢复；
4. **修复**：改成同步 `def`（FastAPI 自动放进 anyio 线程池），bcrypt 在 40 个线程里并行、跨核执行——登录 TPS 4.2→35.7（8.5 倍），进程 CPU 从 88%（1 核）到 1560%（~16 核），混合场景 200 并发线性扩展零错误，假死消失。

规则记忆：**IO 等待用 async；CPU 密集要么同步 def 进线程池，要么 run_in_threadpool / 进程池，绝不能裸跑在循环上。**

## 11. 吞吐拐点怎么判断？

三个信号同时看（阶梯负载每级 2 分钟，取每级后 1 分钟的稳定段）：
1. **RT**：P95 开始陡增（本项目实测：50 并发 P95=16ms → 100 并发 P95≈30~37s，断崖而非缓坡）；
2. **TPS**：用户数增加但 TPS 不再线性增长甚至回落（50 并发 TPS 49.7 → 100 并发 ≈0）；
3. **错误率**：从 0% 开始出现非零（本项目错误不是随请求线性出现，而是悬死 30s 后成批爆发——这是池化资源超时的典型波形）。

注意拐点归因不能只看压测曲线：同一条"RT 飙升"曲线背后可能是 CPU 满（计算瓶颈）、也可能是锁/池等待（本项目，CPU≈0%）。

## 12. 一份合格的压测报告要有什么？

目标 → 环境（含同机声明）→ 场景设计（为什么这么设计）→ 数据表格 + 曲线图 → 瓶颈分析（**证据链**：Locust 数据 + 资源监控 + 现象推理，不能只说"变慢了"）→ 优化方案与**复测对比** → 结论与生产建议。只堆数据的报告不及格，每个数字都要能回答"所以呢？"
